# Архитектура судов Archipelago

Этот документ описывает общий контракт судов. Его цель — не объяснить один `medium-crew-vessel`, а зафиксировать правила, по которым обычная лодка, ходимый корабль, бронекатер и будущие суда могут жить в одной игре без двух параллельных систем.

## Главное правило

**У каждой подсистемы конкретного судна в каждый момент есть ровно один источник истины.**

Нельзя одновременно считать одну и ту же воду в `boat.water` старым ядром и в отсеках новой архитектурой. Нельзя одним `attack` одновременно стрелять из личного автомата и занятой корабельной установки. Нельзя одновременно запускать обычный мотор и пользовательский мотор того же корпуса.

По умолчанию подсистема принадлежит старой лодочной логике (`legacy`). Полноценное модульное судно явно передаёт только нужные подсистемы vessel-архитектуре.

```js
subsystemAuthority: {
  flooding: "vessel-zonal-v2",
  damage: "vessel-zonal-v1",
  repair: "vessel-modules-v1",
  propulsion: "vessel-modules-v1",
  input: "vessel-stations-v1",
  audio: "vessel-custom-v1",
}
```

Если поле отсутствует, считается `legacy`.

## Карта ответственности

| Подсистема | `legacy` | vessel-authority |
|---|---|---|
| движение корпуса | старый free-roam core | отдельный physics module, только если судно его выбрало |
| топливо/температура | старый core | пока legacy, если не объявлен другой owner |
| вода и течи | `boat.water`, `boat.leak` | вода и `leakRate` по физическим отсекам |
| насос | старый глобальный насос | модуль `pump`, здоровье влияет на производительность |
| корпусный ремонт | старый ремонт пластиной | общий vessel hull repair поверх зональных течей |
| ремонт механизмов | отсутствует | физический repair station + конкретный модуль |
| корабельное оружие | старые специальные обработчики | общий `mounted-weapon` station hitscan system |
| личное оружие | combat system | остаётся combat system, если станция не забрала `attack` |
| аудио двигателя | общий light-boat loop | один пользовательский источник на физический корпус |
| палубы | roof/boat legacy | walkable decks, zones, connections, stations |
| сохранение | поля `boat` | deck state + authoritative persistent module state |

## Порядок серверного кадра

Общая последовательность остаётся единой:

1. `before-input` — vessel-система видит исходный ввод.
2. Старый input pipeline получает только то, чем он имеет право владеть.
3. `after-input` — общие действия возвращаются legacy только если vessel station их не забрала.
4. `before-step` — vessel-системы подготавливают authority state.
5. Старый free-roam core считает общую физику, столкновения, топливо и другие legacy-подсистемы.
6. `after-step` — vessel-системы переводят реальные последствия старого core в собственные authoritative состояния.
7. Состояние сохраняется и реплицируется клиентам.

Это позволяет переиспользовать проверенную старую физику без второго параллельного расчёта воды или оружия.

## Ввод: одно действие — один владелец

`vessel-deck-input-bridge-system.js` сначала сохраняет исходные общие команды:

- `attack`;
- `pump`;
- `repair`;
- `guide`.

После обработки палубы команда возвращается обычной игре только если занятая станция её не владеет.

Примеры:

- игрок просто ходит по палубе → `attack` остаётся личному оружию;
- игрок занял корабельную установку → `attack` получает только установка;
- игрок занял пост ремонта двигателя → `repair` получает только двигатель, корпусная пластина одновременно не ставится;
- игрок занял пост ремонта помпы → `repair` получает только помпа.

При передаче ownership очищается и предыдущий legacy-trigger. Это не позволяет старому combat-коду принять переход за отпускание личной атаки и случайно выполнить ещё один удар.

## Палубы и отсеки

Ходимое судно описывается геометрией, а не набором специальных кнопок.

Основные сущности:

- **deck** — физический уровень;
- **zone** — отсек внутри deck;
- **connection** — дверь, люк, лестница или другой переход;
- **station** — физически занимаемый пост;
- **landmark** — доступная навигационная точка.

У `medium-crew-vessel` сейчас три физические части:

1. кормовой отсек — две оружейные установки;
2. рубка — водитель и пассажир;
3. машинное отделение — двигатель и трюмная помпа.

Между кормой и рубкой находится герметичная дверь. Между рубкой и машинным отделением — герметичный люк. Закрытый герметичный переход действительно блокирует передачу воды; открытый пропускает её с заданной скоростью.

## Зональное затопление

Для судна с `flooding: vessel-zonal-v2` старое `boat.water` больше не является физическим резервуаром воды.

Физическая вода хранится в:

```text
instance.zones[zoneId].flooding
```

Физическая течь хранится в:

```text
instance.zones[zoneId].leakRate
```

`boat.water` и `boat.leak` остаются только совместимыми сводными значениями для старого интерфейса, магазина, статуса и систем, которым пока нужен общий показатель.

Перед старым шагом zonal-authority временно не позволяет legacy core считать воду, насос, аварийное утопление и корпусный ремонт этого судна. После старого шага реальные столкновения и старый боевой урон переводятся обратно в зональные повреждения.

### Старые сохранения

Сохранение, в котором старая bridge-система уже размазала одинаковую воду по всем отсекам, мигрируется один раз. Общее количество воды сохраняется, но раскладывается по реальным отсекам.

После миграции в persistent zone state ставится `floodAuthorityVersion = 2`. Поэтому законная ситуация, когда позже несколько отсеков случайно имеют одинаковый процент воды, не будет ошибочно мигрирована повторно после перезахода.

## Повреждение механизмов

`damage.mode = zonal` определяет, какой отсек получил попадание.

В отсеке может быть один модуль или несколько кандидатов. Если кандидатов несколько, урон направляется в наиболее исправный доступный механизм. Благодаря этому серия попаданий по машинному отделению естественно распределяет повреждение между реальными механизмами, а результат не зависит от случайного локального счётчика, который можно сбросить переподключением.

Для medium машинное отделение содержит как минимум:

- `engine`;
- `bilge-pump`.

Поэтому помпа — настоящий повреждаемый модуль, а не декоративный ремонтный объект.

## Насос

Помпа имеет собственные:

- `health`;
- `enabled`;
- `active`.

Повреждённая до нуля помпа не откачивает воду. Частично повреждённая помпа работает слабее. Если игрок пытается включить полностью сломанную помпу, игра сообщает, что её надо ремонтировать в машинном отделении.

После ремонта помпа не включается сама: игрок должен снова дать обычную команду насоса.

## Ремонт двигателя и помпы

Ремонт модулей — физическое действие.

Игрок должен:

1. попасть в нужный отсек;
2. подойти к repair station;
3. занять его действием;
4. удерживать команду ремонта.

На время обслуживания модуль выключается.

Для двигателя это означает:

- двигатель глушится;
- газ сбрасывается;
- судно не получает тягу во время обслуживания;
- после успешного ремонта двигатель проходит обычный lifecycle запуска, а не мгновенно оживает в том же кадре.

Для помпы:

- откачка прекращается;
- после ремонта помпа остаётся выключенной до новой команды насоса.

Один непрерывный hold ремонта может потратить максимум одну пластину. Для следующей пластины игрок должен отпустить и снова удержать ремонт. Это предотвращает случайное уничтожение всего запаса ресурсов доступным hold-контролом.

Если игрок:

- отпустил ремонт;
- покинул пост;
- покинул корабль;
- умер;
- отключился и потерял claim;

незавершённый ремонт отменяется, прогресс и owner очищаются, а модуль возвращается в разрешённое правилами состояние. Длительный ремонт не может остаться без владельца завершения.

## Сохранение модулей

Для судов с vessel-authority стабильное состояние статических модулей хранится в `vesselRuntimeState.version = 2`.

Сохраняются только поля, объявленные `persistentStateFields` у типа модуля. Например:

- двигатель: `enabled`, `health`;
- помпа: `enabled`, `health`;
- установленное оружие: `enabled`, `health`, `ammo`.

Временные процессы специально не сохраняются:

- `repairProgress`;
- активный repair owner;
- текущая защёлка hold;
- кратковременные cooldown/служебные значения, если они не объявлены persistent.

Поэтому двигатель с `health = 0` после перезахода остаётся сломанным, но полузавершённый ремонт не продолжается сам.

## Аварийное затопление

Для zonal vessel старое мгновенное правило «общая вода дошла до 100 → всех выбросило» отключено.

Критическая авария начинается, когда:

- корпус физически разрушен; или
- все водные отсеки полностью затоплены.

После этого остаётся аварийное время на борьбу за живучесть. Только провал этого lifecycle окончательно переводит судно в `sunk` и выбрасывает оставшихся людей в воду.

Герметичные двери имеют смысл на всём протяжении аварии.

## Корабельное и личное оружие

Станция `mounted-weapon` получает `attack` только от физического владельца станции.

Тот же input в этот момент не попадает в личный автомат/пистолет/рукопашный бой.

Если игрок покинул установку, личное оружие снова получает обычный `attack` без отдельной схемы управления.

Личное оружие также обязано уважать настоящий `hullMax`. Старый предел 100 не может обрезать корабль с корпусом 220 или бронекатер с большим корпусом.

## Аудио двигателя

Пользовательский двигатель не подключается напрямую к `AudioContext.destination`. Он всегда проходит через общий `FreeRoamAudio.master`, поэтому общие настройки и остановка аудио действуют и на него.

Для medium:

```text
/assets/audio/vessels/medium-crew-engine-test.mp3?v=3
```

Правила:

- один физический корпус → один audio source;
- локально на борту источник центрирован;
- удалённый корпус позиционируется по настоящим координатам;
- громкость/фильтрация/скорость зависят от дистанции, скорости и газа;
- `sunk`, `reserved`, `engineStalled` или отключённый engine module гасят двигатель;
- общий обычный light-boat motor на этом корпусе подавляется;
- первая неудачная загрузка MP3 не навсегда убивает мотор: клиент делает ограниченные повторные попытки;
- HTML/JSON вместо аудиофайла отвергаются;
- `stopAll` гарантированно закрывает созданные engine sources при смене мира.

## Торговец и восстановление

Полный сервис/аварийный подъём должны изменять реальное состояние, а не только видимые проценты.

После сервиса zonal vessel:

- закрываются зональные `leakRate`;
- полный сервис осушает отсеки;
- reset-ятся flood-disabled состояния;
- восстанавливаются допустимые модули;
- новая жизнь судна не начинает течь на следующем кадре из оставшейся старой пробоины.

## Как добавлять новое судно

1. Создать definition под `public/src/vessel/definitions/`.
2. Выбрать preset или явно определить capabilities.
3. Объявить `subsystemAuthority` только для реально заменяемых подсистем.
4. Описать decks/zones/connections/stations/mounts/modules.
5. Зарегистрировать definition только через `vessel-content-manifest.js`.
6. Если нужен общий runtime system — добавить его под `vessel/systems/` и зарегистрировать через `vessel-plugin-manifest.js`.
7. Не добавлять `if (boatType === "my-new-boat")` в generic free-roam core.
8. Не создавать вторую систему воды, урона, смерти, аудио или ввода рядом с существующей.
9. Добавить saved-world migration, если меняется persistent state.
10. Добавить tests для нормального пути, ошибочного пути, старого сохранения и взаимодействия с legacy лодкой.
11. Пробить browser cache-buster для изменённой клиентской цепочки.
12. Только после этого проверять вручную Safari/VoiceOver и сетевую игру вдвоём.

## Что должно оставаться legacy

Не нужно переводить обычную лодку на новую подсистему только ради единообразия.

Если `standard` нормально обслуживается старым кодом, её authority остаётся `legacy`. Новая архитектура нужна для расширения возможностей конкретного судна, а не для переписывания всей игры без причины.

Это и есть основной контракт: **единая игра, но подсистема выбирает одного владельца; новый vessel-код расширяет старый мир, а не запускает второй мир рядом с ним.**
